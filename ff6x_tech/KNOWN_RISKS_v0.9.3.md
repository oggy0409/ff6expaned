| R68 | **QA party normaliser** `QaCelParty93`, used by the Celes-enabler hub entries (WoR, Praetor locked / QA-scaled, walk-in). It removes Wedge / Vicks, clears Magitek status on all 16 records, sets Terra's field vehicle to none (event `$44`), and uses preset P1 when nobody but Terra is in the party. A party chosen with a preset (P1-P5, E5 presets) is kept as chosen. | QA only | Selftest 58 (every path that starts `$FA` / `$F9`, loads `$1A2` or loads the WoR aboard the airship calls it first); visual suite N1a-d. |
| R69 | The **older QA trees** (v0.9 / v0.8 / v0.7 menus under `Older QA`) are unchanged. Their own battles (e.g. `Battle test (guards)`, vanilla Narshe formations) keep their accepted v0.9 behaviour and do not use the normaliser; the `Opening party (Magitek)` preset deliberately restores Magitek. Use a Celes-enabler entry (or a party preset) before testing Celes content. | QA only, by design | The frozen v0.9 tree must stay byte-identical; the accepted v0.9 QA passed with it. |
| R70 | **Magitek battle mode overwrites monster cells rows 0-11 × cols 12-15** (vanilla engine). Any formation whose used cells reach that area renders armor tiles when a party member has Magitek status. This is vanilla behaviour, and it is why `magitek_possible` exists (formation_safety, R13). The Celes arc (`$244/$245`) and the World of Ruin never have a Magitek party in the real game. | Info (vanilla) | `VRAM_AUDIT_v0.9.3.md`: v0.9.2 path = 12 Bit cells / 10 Lunaris cells overwritten, v0.9.3 = 0. A future content event that keeps Magitek armor into a non-Magitek-safe battle must use a Magitek-safe VRAM map. |
| R71 | **E8 states are drawn by event cmd `$73` in the map startup event** on every load of `$1A2`. A future script that changes the bits *while the player is on `$1A2`* must also redraw with the same `set_tiles` lines, otherwise the change shows only after the next load. | Rule (future content) | `maps/celes_outer_v092/states.json` is the single source; the builder asserts the event lines equal it. |
| R72 | E8 state tiles are restricted to **impassable** tiles wherever they touch the floor. The builder runs the movement model for all 9 combinations. The first stone design used walkable floor plates (`C4 C5 D4 D5`) and was refused. | Rule | Selftest 57; `MAP_STATE_VISUAL_AUDIT_v0.9.3.md` §3. |
| R73 | The archive "kept" shelf tile `BB` / `CB` is **BG-animated** (tileset animation, map property 27). Frame-exact comparisons of that region must allow the animation phase. | Info | Visual suite S4d / S4e compare against a 64-frame in-session series. |
| R74 | **Second emulator.** The visual suite runs on bsnes (accurate PPU, GPLv3, built locally by `tools/build_bsnes_core.sh` with a small harness patch: memory dumps and a gamma override; the emulation itself is unchanged) and on snes9x. Mesen2 / hardware are still covered only by your runtime QA. | Info | `tools/emu_bsnes.py`; bsnes and snes9x agree on every S1-S4 result (before and after). |
| R75 | S2 (WoR dog) forces the Lunaris formations through a **temp ROM copy**: the landing sector's random-battle groups point at `$CB` / `$CA`. Only that table is patched in the copy; the graphics path is the real one. |
| R76 | The QA root title now says `TECH v0.9.3 QA ACCESS`; the menu ids and options are unchanged. | QA only | — |
| R77 | **bsnes harness and battery RAM.** The libretro core reads and writes `<save dir>/<rom>.srm`. With a shared save directory, a save written by one test run made the title screen of the next run default to *Continue*, so `boot_new_game` loaded that save instead of starting a New Game (seen once during this cycle's regression: E8 states looked stuck). `tools/emu_bsnes.py` now gives every load a fresh, empty save directory, like stable-retro. A second harness defect showed up after that: reloading a different ROM in the same process after a field-map session crashed in `SMP::readIO $F4` (the SMP cothread resumed against the old CPU thread). Every reload now runs `retro_deinit` / `retro_init` as well. Every bsnes result in `REGRESSION_REPORT_v0.9.3.md` comes from runs after that fix. | Test tooling (fixed) | Debug check: event bits `$0E0-$0EC` = 0 right after New Game on bsnes; S4 RESET tiles = layout. |
| R78 | **White cast flash on a Bit.** Right after the 70% reveal, a Bit casting Rflect is drawn for about 20 frames as a white silhouette (vanilla effect when a monster casts). It can be mistaken for corruption. The visual suite waits for it to end (bounded at 600 frames) before it samples. | Info (vanilla) | `S3_*_transient_before_settle.png`. v0.9.3 settles in 20 frames; v0.9.2 never settles (armor tiles). H3 in the guide mentions the flash. |
