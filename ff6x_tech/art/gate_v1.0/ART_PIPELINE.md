# ART PIPELINE — source PNG → ROM (ART ASSET GATE v1.0)

This is the workflow the art pass will follow. **The builder and its source assets stay the only source of truth.** Every
ROM byte is regenerated by `build.py` from files in the repository. There is no manual FF6Tools / hex edit, no edited ROM
as an input, and no binary blob without its source.

This gate only documents the pipeline. Steps 3-8 need builder code that does not exist yet; it is a future TECH milestone
and is not started here.

## 0. Inputs the artist receives (this package)
* `MAP_1A2_CURRENT.png` / `_1X.png`, `MAP_1A2_RUNTIME_*.png`: context at 1:1 and annotated.
* `MEMORIAL_REGION.json`, `ARCHIVE_REGION.json`, `REGION_*.png`: exact rectangles, current tiles, neighbours, collision.
* `PALETTE_1A2.png` / `.json`: the 128 colours (BGR555), rows, engine-managed colours.
* `TILESET_1A2_8X8_IDS.png`, `METATILES_1A2_*`: everything the room already draws, by id.
* `VANILLA_REFERENCE/`: style references; ids and graphics of each candidate.
* `CUSTOM_ASSET_SPEC.md`: size, colour, collision and capacity rules.

## 1. PNG (concept → final)
* Concepts can be in any format. The **final** asset is one PNG per state:
  * `memorial_tags.png` 64 × 32;
  * `memorial_stone.png` 64 × 32 (or 64 × 48);
  * `archive_kept.png` 32 × 32;
  * `archive_burned.png` 32 × 32;
  * optional `archive_sealed.png` 32 × 32.
* Each is drawn on an 8 × 8 grid aligned to the region origin. Mock it up in `MAP_1A2_CURRENT_1X.png` to check the fit
  with the wall.
* Proposed repository location: `art/e8_v1.0/` (PNGs + `art.json`), next to `maps/celes_outer_v092/states.json`.

## 2. Indexed palette
* The PNG is **indexed**. Every 8 × 8 cell uses colours of **one** palette row: index 0 (transparent) + up to 15 colours.
* `art.json` maps each cell to a palette row and gives the row contents as BGR555. Rows 4-6 can hold new colours; rows
  2/3 are the room's floor / wall colours.
* Colours are stored as BGR555, so RGB888 values are quantised to 5 bits per channel. The pipeline reports any colour
  that changes when quantised.
* Rejected:
  * a cell mixing rows;
  * a cell with more than 15 colours;
  * any use of CGRAM 1-3 / 121-127;
  * index 0 inside an area meant to be dark (index 0 shows as black, see the spec).

## 3. 8 × 8 tiles
* Slice the PNG into 8 × 8 cells and convert each to SNES 4 bpp planar (32 bytes; planes 0/1 interleaved by row, then
  planes 2/3).
* This is the inverse of `ff6x/fieldgfx.tile_pixels`, so it is round-trip testable.

## 4. Dedupe / flips
* Identical cells are stored once. So are cells that are h-, v- or hv-mirrors of a stored cell (BG word flip bits 14 / 15).
* Blank cells may map to one shared tile.
* Allocation into the free VRAM tile numbers of the cloned graphics set (`CAPACITY_1A2.json`):
  * slot 4: 148 free;
  * never `$280-$2BF` (animation);
  * never `$2E0-$2FB` (window).
* The allocation is written to `art.json` (or generated deterministically and recorded in the build manifest).

## 5. Metatile composition
* Each 16 × 16 metatile = 4 BG words (TL, TR, BL, BR): `tile | row << 10 | priority 0 | flip bits`.
* New metatiles take ids from the list "not on $1A2 and impassable in property set `$24`" (145 ids, `CAPACITY_1A2.json`).
  The collision is therefore correct without new property data.
* The cloned tileset (`$22` copy → new index `$4C`) gets these ids. Everything else stays byte-identical to `$22`.

## 6. Tilemap / state definition
* `states.json` rows (one per state) list the new metatile ids, in row-major order of the region.
* The startup-event `set_tiles` lines are taken from `states.json`, as they are today (the builder already asserts that
  they are equal).
* The accepted E8 bits / selection stay unchanged.

## 7. Builder injection (future TECH milestone)
* New allocation regions in `GRAPHICS_RESERVED_FE` (`MAPX_GFX`, `MAPX_TILESET`).
* Vanilla-space claims for the free pointer slots (map graphics `$52` at DF:DAF6, tileset `$4C` at DF:BAE4).
* `$1A2` property-row bytes 9-12 re-encoded to the new graphics set (slot 4) and tileset.
* Fail-closed checks:
  * vanilla graphics sets / tilesets / property set `$24` byte-identical;
  * frozen ROMs byte-exact;
  * every tile used by the original `$1A2` metatiles kept in the clone;
  * all state tiles impassable;
  * the 9-combination movement model unchanged;
  * palette rules from step 2.

## 8. Rendered screenshot verification
* Static: `tools/art_gate_v10.py` renders the map from the built ROM in every state. These are the region crops and
  `MAP_1A2_STATES.png`.
* Runtime: `tools/art_gate_capture_v10.py` (bsnes, accurate PPU) captures VRAM / CGRAM / tileset / BG1 and screenshots of
  RESET / PRESERVE / BURN / GRAVES. The export then requires:
  * ROM decode = runtime (VRAM, CGRAM excluding engine colours, tileset, BG1 = layout + `states.json`);
  * E8 regions pixel-exact;
  * all remaining screen differences in sprite cells only.

  This is the check that `VERIFICATION_v1.0.json` already passes for the current placeholders.
* Then a human check: before / after contact sheets, and the user runtime QA on real emulators / hardware.

## 9. Reproducing this gate
* Runtime capture:
  ```
  FF6X_EMU=bsnes python3 tools/art_gate_capture_v10.py out/FF6X_Rev1_TECH_v0.9.3_VISUAL_STATE_VRAM_HOTFIX_QA.sfc <capture dir>
  ```
  The bsnes core comes from `tools/build_bsnes_core.sh`.
* Export (read-only; writes only `<out dir>`):
  ```
  python3 tools/art_gate_v10.py out/FF6X_Rev1_TECH_v0.9.3_VISUAL_STATE_VRAM_HOTFIX_QA.sfc "<clean Rev 1>.sfc" <capture dir> <out dir>
  ```
